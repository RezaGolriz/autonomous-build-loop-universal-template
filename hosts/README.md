# Hosts and providers

A client host is where the human operates the loop. A worker provider is the
separately installed AI CLI that performs one bounded node. These roles may use
the same product name but they are not the same connection.

| Component | Example | Responsibility |
|---|---|---|
| Client host | Codex chat or Claude Desktop | Presents status, proposals, blockers, and approval UI |
| Control interface | Node CLI, project-bound MCP, or shell orchestrator | Dispatches operations to the policy engine |
| Worker provider | Authenticated Codex CLI or Claude Code CLI | Produces one node artifact or independent review verdict |

Installing a Claude Desktop extension does not authenticate Claude Code.
Installing a Codex skill does not install a Codex CLI account. Run doctor to
check the selected provider on the machine that will execute it.

The current package and Claude Desktop extension target macOS and Linux. Native
Windows is unsupported and unvalidated because the control engine depends on
Bash, Unix tools, and Unix process behavior.

A worker invocation can send its bounded node input, project content, exact
change, or review evidence to the selected model provider. Keep secrets out of
scope and review that provider's data controls before enabling it.

## Install the Codex plugin

The distribution's Codex plugin contains the build-loop skill and bundled CLI
runtime. From a source checkout, build it first with `npm run bundle`. Then
register the generated local marketplace and install the plugin:

~~~bash
codex plugin marketplace add /absolute/package-root/dist/codex
codex plugin add build-loop@build-loop-local
~~~

Start a new Codex task after installation so it loads the skill. Open the target
repository as that task's project. The plugin can operate through its bundled
CLI without running an MCP server. The skill resolves the CLI from its own
plugin directory, while the target root comes from the current Codex project
and is passed explicitly.

MCP is optional for Codex. If configured, start a separate project-bound server
for each target. Do not describe optional MCP configuration as automatic project
root discovery.

The source host adapter uses hosts/codex/provider.sh and the Codex CLI. Set
machine-specific executable configuration outside the project adapter. Keep
authentication in Codex's own credential store.

## Install the Claude Desktop extension

The bundled .mcpb local extension is generated by:

~~~bash
npm run bundle
~~~

When the bundle has been built and validated, install dist/build-loop.mcpb in
Claude Desktop. Configure user_config.project_root with the absolute target
directory. The extension launches a project-bound stdio server. The .mcpb does
not bundle Node; Claude Desktop supplies Node to its extension process. Bash,
jq, Git, Perl, target tools, and any selected worker CLI remain machine
prerequisites. Desktop extensions may receive a minimal PATH, so use doctor and
machine-local absolute provider or CLI paths when discovery cannot find an
installed executable.

For untouched bundled Codex or Claude providers found automatically, configure
stores a fixed signed authentication-status check and doctor may execute it.
That provider command may update its own local cache. Custom provider paths and
explicit CLI wrappers remain authentication unknown and doctor reports
ready=false; arbitrary authentication commands are never executed.

Opening a folder or CLAUDE.md in Claude Desktop is instructional context only.
Without the local extension or equivalent MCP configuration, the conversation
cannot call control operations.

The source worker adapter uses hosts/claude/provider.sh and Claude Code. Claude
Desktop's signed-in session does not by itself establish Claude Code CLI
authentication.

## Direct MCP configuration

For a client that supports local stdio MCP servers:

~~~bash
node bin/build-loop-mcp.mjs --root /absolute/path/to/project
~~~

LOOP_PROJECT_ROOT may provide the same fixed root. The MCP tools are named
`loop_<operation>`. The special `loop_request_approval` tool takes no arguments and
opens the local bound confirmation view.

The server must not accept a project-root override in tool input. Create another
server configuration for another target.

The server negotiates MCP protocol versions 2025-11-25 and 2025-06-18. Older
versions are rejected because they do not provide every transport behavior this
implementation requires.

## Project configuration and machine configuration

The project adapter is shared configuration truth: target runtimes, artifacts,
verification commands, evidence kinds, protected paths, and allowed environment
variable names. Provider executable paths, installed versions, and
authentication are machine facts and belong in separate provider machine
configuration.

Do not copy access tokens or provider credentials into project.adapter.json,
work items, approval payloads, or evidence.

## Shell provider contract

The shell orchestrator starts a provider with the target root as its working
directory, a JSON node brief on stdin, and a minimal environment consisting of
the adapter's allowed names plus loop identifiers.

For DEFINE, DESIGN, EXECUTE, VALIDATE, and HANDOVER, stdout is one normalized
JSON result:

~~~json
{
  "schema_version": 1,
  "status": "DONE",
  "defect_class": null,
  "blocker": null,
  "notes": "Bounded summary"
}
~~~

A blocked result uses status BLOCKED and a concrete blocker. Provider stderr is
captured as a log and is never parsed as the result.

For REVIEW, stdout must conform to spec/schemas/verdict.schema.json and echo the
challenge's run ID, work-item ID, nonce, revision, and evidence references.
Review always starts in a fresh process and does not receive the builder's
private reasoning transcript.

Providers exit nonzero on invocation or transport error. They never choose a
state transition, run around a failed verifier, or certify their own artifact.

## Builder and reviewer selection

The builder and reviewer may use the same provider program only when review
still starts in a fresh independent context. Using different providers can
reduce shared blind spots, but provider diversity does not replace nonce
binding, exact-diff review, or evidence validation.

Shell example:

~~~bash
./engine/orchestrator.sh loop --root /path/to/project \
  --host codex --provider hosts/codex/provider.sh \
  --review-host claude --review-provider hosts/claude/provider.sh \
  --max-nodes 12
~~~

The mock provider under hosts/mock is deterministic test infrastructure. It is
not a production worker.
